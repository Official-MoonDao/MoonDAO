## 1. Scorecard

The doc has two halves and they are not the same quality. The **inbound** half (Interactions
endpoint, slash commands) is close to implementable. The **outbound** half (odds wire) is a
distributed-systems problem written as a four-bullet list, and it contains a defect that makes the
wire go permanently silent.

| Rubric group | Verdict | Why |
|---|---|---|
| **Framing** | Adequate | Problem stated before solution; non-goals are unusually good and product-motivated ("should not be scraped into a grey-market Discord bookie"). Blast radius is understated *inside the doc* — a reader of PR-G alone never learns it collides with PR-D on `serverMarket.ts` and on the mocharc. |
| **Decision quality** | **Weak** | G1–G4 are genuinely real alternatives with real rationale — better than the rest of this doc set. But the riskiest technical decision in the PR (type-4 race vs type-5 deferred) is never made: §6.2 says "either (a) … or (b)". Ownership of `serverMarket.ts` is deferred to whichever branch lands first. `/pool` is a whole new Juicebox server read path for a number that barely moves. |
| **Operational rigor** | **Weak** | The worst axis. Post-vs-snapshot write ordering has no success condition; a crash between them produces an unbounded duplicate-post loop; an outcome-set change wedges the wire off forever; `postedAt` is declared in the stored JSON and never read; no cooldown or per-window cap; no Discord 429 handling; no rollback; no observability; the Action goes green while the wire is broken. |
| **Trust & safety** | Adequate | Link-only `/bet` + exact legend + "no forecasts in-bot" is the right architecture, and keeping the gate on the website is correct. Gaps: the wire's own channel post carries no legend, the absence of any geo signal on Discord is never written down, and `/leaderboard` renders user-supplied display names into an embed with no mention suppression. |
| **Verifiability** | **Weak** | The pure detector is testable without Discord — good. But no test fails if Ed25519 verification is disabled or if `bodyParser: false` is deleted; the known vector is allowed to be self-generated by the library under test; and the snapshot-transition logic (the part most likely to be wrong) lives inline in the cron handler where nothing tests it. §7.12 acceptance is mostly test-guild screenshots. |
| **Process hygiene** | **Weak** | Reviewers are roles, not names. The doc never states what decision it is asking for. Five frozen defaults (`5` pt, `*/10`, `"22"`, `sepolia`, `2000 ms`) are asserted with no owner, no rationale, and no revisit trigger. Status is "Ready" with two unresolved implementation forks. |

**Overall: Weak — needs revision before implementation.** Ship-blocking work is concentrated in
§6.4 and §6.6, not spread across the doc.

**Single most important improvement:** the repo already contains the exact pattern this doc needs.
[`ui/lib/deprize/reconcile.ts`](../../ui/lib/deprize/reconcile.ts) lines 80–88 expose
`nextReconcileCursor({ lastProcessedBlock, succeeded, processedThrough })` — a **pure** function
whose doc comment is literally *"On failure the previous cursor is kept so the next run retries the
same range."* PR-G must mirror it with a pure `nextOddsWireSnapshot({ previous, current, posted })`
and make three rules a tested contract: advance only on confirmed delivery, reset the baseline when
the outcome set changes, and suppress within a cooldown window. Everything in §3's failure table
collapses to that one extraction.

## 2. Findings

### Must-fix

**M1. The snapshot key carries three conflicting responsibilities, and the doc's own two rules
compose into a permanent silent wedge.**

`deprize:oddswire:{chain}:{id}` is simultaneously (i) the last-posted probability baseline, (ii) the
dedup token, and (iii) the implicit fingerprint of the outcome set. Those three want different
update rules, and §6.4 gives them one.

The wedge is derivable from the doc without running anything. §6.4 specifies
`shouldPostOddsWire` returns **false** when "lengths differ", and separately specifies that "on
later no-move runs, keep the previous snapshot (do not reset the baseline)." Now supersede a market
or redeploy it with a different outcome count — which is live work on a sibling branch. The stored
baseline has the old length, `shouldPostOddsWire` returns false, the "no post" path keeps the old
baseline, and the length never matches again. **The wire returns false on every run forever and
nobody is notified.** This is the same class of defect the sibling critique found in another PR's
cron — an idempotency key doubling as a data store — with the same outcome (every run after the
first skips its work) reached by a different route.

Recommendation: store `{ p: number[], outcomeCount: number, postedAt: number | null }` and make the
transition explicit and pure:

- `previous == null` → no post, write baseline, `postedAt: null`.
- `outcomeCount` differs → no post, **overwrite** the baseline with `current`, return a
  `reason: 'outcome-set-changed'` in the cron response so the reset is visible.
- non-finite in `current` → no post, **do not** advance (bad RPC read must not poison the baseline).
- move ≥ threshold and within cooldown → no post, do not advance.
- move ≥ threshold, post confirmed → advance baseline and `postedAt`.
- move ≥ threshold, post **not** confirmed → do not advance.

**M2. Write ordering after a successful post is unspecified, and the crash window produces an
unbounded duplicate loop — not a single duplicate.**

§6.4 says "POST embed … then SET the snapshot," with no condition on the post's outcome. Both
interleavings are broken as written:

- If the SET runs unconditionally and the post failed, the baseline advances past a move nobody
  saw. The move is lost permanently, because the baseline is the last-*posted* state — the next run
  compares against odds that were never announced.
- If the post succeeded and the process dies (or Redis SET fails) before the write, the next run
  re-detects the *same* move against the *stale* baseline and posts again. And again, every 10
  minutes, until the odds happen to drift back inside the threshold. A one-off duplicate is
  tolerable; a 10-minute repeating duplicate in a community channel is a page.

Recommendation: make the post's result a discriminated value, not `boolean` (see M6), advance only
on `ok`, and bound the crash window with the `postedAt` cooldown from M3 so the worst case is one
extra post per cooldown rather than one per run. If you want tighter, write a `pending` marker
before posting and reconcile it on the next run. State the chosen ordering and its at-least-once
consequence in the doc — right now the doc's only claim is "Idempotent: same snapshot → no second
post," which is true only on the happy path it already assumes.

**M3. No cooldown or per-window cap. The doc stores `postedAt` and never reads it.**

§9 waves at this: *"a market oscillating 4.9/5.1 can still flap — accept for v1."* That accepts an
unquantified ceiling. A 10-minute cron with a 5-point trigger and no suppression permits **144 posts
per prize per day**, and an LMSR with thin liquidity is exactly the regime where 5 points is a small
trade rather than news. Accepting a risk requires naming the number you are accepting.

The fix is already half-written: the stored JSON shape in §6.4 includes `postedAt`, and nothing in
the doc ever uses it. Add `ODDS_WIRE_MIN_INTERVAL_MIN` (60 is a defensible start) and a per-prize
daily cap, both checked against `postedAt`. This also bounds M2's duplicate loop, which is why it is
Must-fix rather than Consider.

**M4. "Either race 2000 ms or type 5 deferred" is an unmade decision, and the deferred branch
depends on a serverless guarantee the doc never claims.**

§6.2 and §7.6 both offer (a) and (b). A design doc that offers two options with different hosting
requirements and different user-visible failure modes will produce two implementations, and one of
them is quietly broken: on Next.js serverless the invocation is not guaranteed to keep running after
the response is flushed, so "type 5 then PATCH the webhook" can return the ACK and then be frozen
before the PATCH fires. The user sees *"MoonDAO is thinking…"* until the interaction token expires.
That is a worse outcome than the type-4 error copy, and it is invisible in logs.

Three concrete gaps in the deferred branch:

- The follow-up PATCH to `/webhooks/{application_id}/{interaction_token}/messages/@original` needs
  `DISCORD_APPLICATION_ID` **at request time in the interactions route**. §6.5's env table lists
  that variable as used by "register" only. The route will `undefined` its way into a 404.
- No failure copy is specified for the deferred path. §6.2 gives *"Couldn't read the market — try
  the site"* only for branch (a). Specify that a `serverMarket` failure inside a deferred flow
  PATCHes that same string, so the "thinking" state always terminates.
- No statement of what the PATCH's own failure does.

Recommendation: choose branch (a), the bounded race, for v1 — one response, no post-response work,
no token lifetime to reason about, and the 2000 ms budget is a single tunable. Move (b) to a
follow-up gated on an explicit `waitUntil`/`after` mechanism, and record the choice in §5 as a
sub-decision with an owner. If (b) is chosen instead, the doc must name the hosting primitive that
guarantees post-response execution.

**M5. `/leaderboard` renders user-supplied display names into a Discord embed with no mention
suppression. `@everyone` is a display name.**

§6.2 has `/leaderboard` read top-10 from `forecast:lb:2026` and render an embed. Those names come
from PR-D's store, and per the review's shared-artifact table the 40-char/no-`://`/no-raw-IP
sanitizer is PR-C's. Neither of those is mention suppression, and §6.4's "Always
`sanitizeDiscordEmbeds`" is about embed *shape* — it is invoked for the wire helper only, and it is
not an escaper. A forecaster who sets their name to `@everyone` gets the bot to ping the guild every
time anyone runs `/leaderboard`; `](https://evil.example)` smuggles a link out of a name.

Recommendation: set `allowed_mentions: { parse: [] }` unconditionally inside
`postDiscordChannelMessage` **and** on every interaction response body, and escape Discord markdown
in any string that originated from a user. Put the escaper next to the helper so there is one of
them. This is the cheapest systemic fix in the review and it currently appears nowhere.

**M6. Observability is absent, and `curl -fsS` will keep the Action green while the wire is dead.**

[`.github/workflows/deprize-reconcile.yml`](../../.github/workflows/deprize-reconcile.yml) line 20
is the template PR-G copies: `curl -fsS` fails the job only on a non-2xx. §8 then instructs the wire
to return **200** `{ skipped: true }` when the channel id is unset, "do not 500 the Actions job."
Compose those and a permanently misconfigured or permanently failing wire is a green checkmark every
ten minutes. There is no counter, no structured log line, and no alert path, even though a webhook
alert channel already exists in this codebase for compliance.

Recommendation: define the cron's response shape in the doc — `{ checked, posted, skippedCooldown,
resetBaseline, errors: [{ prizeId, reason }] }` — so the Action log is inspectable, and either
return non-2xx on hard failure or add a `jq` assertion on `errors == []` in the workflow. Decide
explicitly whether N consecutive post failures alert to the existing compliance webhook or stay
silent; either answer is fine, silence by omission is not.

**M7. The wire's own channel post has no availability legend, and the absence of a geo signal on
Discord is never stated.**

§6.2 requires `/bet` to carry the exact `DEPRIZE_AVAILABILITY_LEGEND` — correct. But the odds wire
is a *proactive broadcast* to a channel whose membership certainly includes restricted
jurisdictions, and §6.4 specifies its content only as "embed." An unsolicited "Touchdown just moved
6 points" push is a stronger solicitation than a user-initiated `/odds`, and it is the one surface
with no legend requirement attached.

Worse, the load-bearing assumption behind the whole design is missing from the doc. The non-goals
forbid in-Discord betting as *policy*; they never state the *reason*, which is that Discord provides
no reliable jurisdiction signal. Because the reason is unwritten, it cannot be applied to a case the
non-goals did not enumerate — and the next person to propose a "Bet 0.01 ETH" button will read the
non-goals as an arbitrary v1 scope cut.

Recommendation: (a) require the wire embed's footer to be the availability legend constant — the
same constant, not hand-written copy that drifts; (b) add one sentence to §4 as a standing
constraint: *Discord gives us no reliable jurisdiction signal, therefore no Discord surface may ever
be the last gate before a bet; the website gate is the only gate.* The design already honors it;
write it down so it binds.

**M8. No test fails if Ed25519 verification is disabled, and the known vector may be self-generated
by the library under test.**

§6.1 permits the fixture to come from Discord's examples **"or a locally generated Ed25519 pair."**
A pair generated by the same library you are testing proves self-consistency, not conformance to
Discord's signing scheme — and it will keep passing if you later swap `discord-interactions` for
`tweetnacl` incorrectly. Separately, §6.6's two tests both target pure helpers, so nothing detects
the two most likely regressions: someone deletes `export const config = { api: { bodyParser: false } }`,
or someone comments out the verify call while debugging. Both leave a green suite and an open
endpoint.

Recommendation: pin committed hex constants (public key, signature, timestamp, body) for one
positive vector plus three negatives — flipped signature byte, altered body, altered timestamp — and
add two handler-level tests: an unsigned POST to the exported handler asserts **401**, and an
assertion that the route module's `config.api.bodyParser === false`. The second is a three-line
import-and-assert that fails the instant the export is removed. That is the test the rubric is
asking for, and the doc has no equivalent.

**M9. Reviewers are roles, and five frozen defaults have no owner or revisit trigger.**

The header lists "DePrize product, engineering, ops (channel IDs)". The doc never states what
decision it wants. Concretely it needs three: the ACK strategy (M4), the cooldown/cap values (M3),
and the guild plus channel ids. Only the third is flagged, assigned to "Ops," unnamed.

`ODDS_WIRE_THRESHOLD_PT = 5` is the entire signal-versus-spam tradeoff and is asserted with no
rationale whatsoever — why 5 and not 3 or 10, and is 5 above or below noise on a thin LMSR? Same for
the `*/10` cadence, the `2000 ms` race budget, default `prize = "22"`, and default `chain =
sepolia`. The last two will rot the moment Touchdown moves to Arbitrum, which §6.2 anticipates
("until an Arbitrum Touchdown exists") without assigning anyone the migration.

Recommendation: a table of frozen defaults with owner and revisit trigger, e.g. *"threshold 5 pt —
owner: DePrize product — revisit if the wire posts more than 6× in a day for a week."*

### Should-fix

**S1. `postDiscordChannelMessage` returning `Promise<boolean>` erases the information the cron needs
to decide.** A boolean makes 429 (retry, do not advance), 403 missing-permission (permanent, alert
ops, stop retrying), 404 wrong channel id (permanent, config error) and 500 (retry) indistinguishable
— so the cron cannot implement M1's transition even if it wants to. Return `{ ok: true } | { ok:
false; status: number; retryable: boolean }`. Honor `Retry-After` once on a 429, then report
non-retryable. Discord's per-channel message limit is tight enough that a loop over several watched
prizes (§6.4 anticipates "plus any `CAPABILITY_LADDER` live id") can hit it, and the doc mentions
Discord API rate limits nowhere.

**S2. "Optionally refactor `send.ts`" contradicts the reason for the extraction.** §7 step 3 says
*"Implement `postDiscordChannelMessage`; optionally refactor `send.ts` to use it
(behavior-preserving)."* The stated justification for extracting the helper is that there should be
one implementation of the channel POST. Making the second call site optional guarantees two. Make it
mandatory in the same PR, and spell out what behavior-preserving means concretely: today
[`ui/pages/api/discord/send.ts`](../../ui/pages/api/discord/send.ts) throws on `!response.ok` and
returns 500, so with a boolean-returning helper the route must reconstruct that throw — which is
another reason to prefer S1's result type. While you are there, note that `channelIds?.[type]`
(line 21) lets an unknown `type` POST to `/channels/undefined/messages`; the extraction is the
moment to validate a non-empty `channelId` in the helper rather than propagate the hole to a second
caller.

**S3. `serverMarket.ts` ownership is resolved by whoever runs first.** §7 step 5: *"Add
`serverMarket.ts` if PR-D has not … do not duplicate if it already exists."* That is not a decision,
it is an instruction to inspect branch state at implementation time — and the review's §2.4 table
already flags "two RPC conversions, two `state()` probe bugs" as the cost. The review's sequencing
puts G at step 4, after D. Commit to that in PR-G's own dependency line with a named integrator, or
declare that G vendors the file and D rebases onto it. Pick one; the doc currently ships the
ambiguity.

**S4. IP-keyed `rateLimit` on an endpoint whose only legitimate caller is Discord is a self-DoS, and
Discord will retry into it.** §6.2 applies the existing `rateLimit` middleware and §6.2 adds "Rate-limit
abusive guilds via existing `rateLimit`." That middleware cannot see guilds — it sees the source IP,
and every interaction arrives from Discord's small egress set. So the limiter is effectively global
across all guilds and all commands: one busy guild degrades the bot for everyone. And a 429 to
Discord is a non-2xx, so Discord retries, the retry is also limited, and the user gets "application
did not respond." Recommendation: verify the signature first (it is already the real
admission control — an unsigned request cannot be forged), then rate-limit on `guild_id` /
`member.user.id` from the *verified* payload, and respond **200 with an ephemeral message** when
throttled rather than 429. Keep a coarse IP limiter only as a flood backstop, sized well above
Discord's aggregate volume.

**S5. No replay protection, and the reason it is currently harmless is unwritten.** Ed25519
verification proves authenticity, not freshness: a captured valid interaction body replays forever.
Today every command is a read or a link, so a replay is harmless — but that is a property of the
current command set, not of the endpoint, and it evaporates the first time someone adds a
state-changing command. Recommendation: reject `X-Signature-Timestamp` outside a ±5 minute skew
window (two lines, no storage), and if you decline, write the dependency down as a constraint on
future commands rather than leaving it implicit.

**S6. No rollback, and the bot half has no un-register path.** §8 has Rollout and no Rollback.
Working out the kill switches from what is written: the wire's is unsetting
`DEPRIZE_ODDS_WIRE_CHANNEL_ID`, which needs an env change plus a redeploy when the fast lever is
right there — disable the workflow schedule and leave `workflow_dispatch`. The bot's stated switch is
unsetting `DISCORD_PUBLIC_KEY` for a 503, but repeated failures are how Discord decides to disable
your interactions URL, so that "rollback" costs a re-validation to undo. The clean rollback is
`PUT` an empty command array to the guild endpoint — instant, reversible, leaves the endpoint
healthy. §6.3's register script has no such mode. Add `yarn discord:register --clear` and write both
levers into §8.

**S7. Blast radius is invisible to a reader of PR-G alone.** The collision table lives in
[`pr-design-docs-review.md`](pr-design-docs-review.md) §2.3–2.4, which will not be attached to the
PR. PR-G shares `ui/lib/deprize/serverMarket.ts` and `ui/scripts/.mocharc-deprize-unit.json` with
PR-D, and takes ownership of `postDiscordChannelMessage` on behalf of `send.ts`. Put those three
rows in PR-G §4 or §10 so the implementer sees them without the review file.

**S8. §7.12's acceptance criteria test the happy path and are not repeatable.** "Confirm **one**
channel message; run again with the same live odds → **no** second message" depends on live odds
holding still, and none of the criteria touch the paths that will actually break: post fails →
baseline unchanged → next run retries; crash after post → does it double-post; outcome count changed
→ does it reset. Recommendation: move those three to unit assertions on `nextOddsWireSnapshot`
(which is why M1's extraction is also the verifiability fix) and keep exactly one manual smoke test
in the guild for the Discord round-trip. §6.6's existing list is otherwise good and specific —
+5.0 posts, +4.9 does not, NaN is false — keep it and add the transition cases.

### Consider

**C1. `/pool` is the weakest value-to-cost item in the PR.** It requires a fresh server-side
Juicebox read path — `balanceOf` plus `usedPayoutLimitOf`, including the magic `2` copied out of
[`useTotalFunding.tsx`](../../ui/lib/juicebox/useTotalFunding.tsx) lines 29–44 without being named —
for a number that changes on a scale of days and is already on the site. Consider making `/pool` a
link like `/bet` in v1 and spending the effort on M1. If it stays, name that `2` in a shared
constant rather than duplicating an unexplained literal into a second call site.

**C2. Do not register `/leaderboard` until PR-D lands.** §6.2's degraded reply is "Leaderboard ships
with free forecasts — {site}/deprize/leaderboard". A registered command that answers "this feature
does not exist yet" is worse than an unregistered one, and §6.3 already establishes that guild
commands propagate immediately — so adding it later is free. Gate registration on the store
existing.

**C3. `yarn discord:register` is an ops action with a bot token, run from a laptop.** Worth one line
in §6.5 stating that the token comes from the ops secret store, that the script is never a CI step
(or, if it is, which secret it reads), and that it refuses to run against a global scope in v1 —
§6.3 says "do not register globally," which is a rule the script itself should enforce alongside the
`DISCORD_GUILD_ID` check it already has.

**C4. Malformed Redis JSON is unhandled.** A partial or hand-edited snapshot value will throw inside
the cron and produce a red Action with no diagnosis. Treat an unparseable value as `previous = null`:
no post, reset the baseline, report the reset. `parseStoredCursor` in
[`reconcile.ts`](../../ui/lib/deprize/reconcile.ts) lines 90–95 is the in-repo precedent for
defensively parsing stored state, and it is tested.

**C5. Overlapping runs.** A `workflow_dispatch` during a scheduled run gives two invocations the same
baseline and two posts. A `SET NX EX` lock per prize is cheap and removes the class.

### Where the design is right

Verify-before-parse with `bodyParser: false`, fail-closed 401 on a bad signature and 503 on a
missing public key, `rateLimit` instead of `authMiddleware` (`send.ts` line 46 is Privy-gated and
[`sendDiscordMessage.tsx`](../../ui/lib/discord/sendDiscordMessage.tsx) is a browser `fetch` at line
11, so neither is reachable from a cron), reusing `maxProbDelta` rather than inventing a second
delta, STRING `prize`, guild-scoped registration first, the graceful `/leaderboard` and `/forecast`
degradation when PR-D is late, and `authorizeCronRequest` / `cronSecretFromRequest`
([`reconcile.ts`](../../ui/lib/deprize/reconcile.ts) lines 109–129) for the wire. Also worth naming
explicitly since the doc does not: **every interaction handler is a read or a link, so Discord's
redelivery of an interaction is idempotent by construction.** That is a real property earned by the
non-goals — state it in §4 so it is defended rather than accidental.

## 3. Failure-mode table — odds wire

| # | Failure point | Current behavior per the doc | Recommended behavior |
|---|---|---|---|
| 1 | First run, no snapshot | No post, SET snapshot (§6.4, explicit) | Keep. Also persist `outcomeCount` and `postedAt: null`. |
| 2 | Move ≥ 5 pt, post OK, SET OK | One post | Keep. This is the only path the doc covers. |
| 3 | Move ≥ 5 pt, **post fails** (429 / 5xx) | Unspecified. "POST … then SET" with no success condition; if SET runs, the move is lost permanently | Do not advance the baseline. Classify retryable from status. Surface in `errors`. |
| 4 | Move ≥ 5 pt, post OK, **process dies before SET** | Next run re-detects the same move against the stale baseline and posts again — every 10 min until the odds drift | Cooldown via `postedAt` bounds it to one extra post per window; optionally a `pending` marker written before the post. |
| 5 | Move ≥ 5 pt, post OK, **Redis SET fails** | Same unbounded duplicate loop as #4, silently | Same fix, plus treat SET failure as a hard error in the response so the Action log shows it. |
| 6 | **Outcome count changes** (supersede / redeploy) | `shouldPostOddsWire` false, and "keep the previous snapshot" never updates the baseline → **false forever, wire silently dead** | Overwrite the baseline with `current`, do not post, report `reason: 'outcome-set-changed'`. |
| 7 | **Prize resolves** | Unhandled. Probabilities jump toward 100/0 → the wire posts a fake "94-point move" as if it were market action | Read prize state in the loop; skip resolved and superseded prizes. Optionally one terminal "resolved" post, then stop watching. |
| 8 | Market oscillates 5.1 pt around the baseline | Posts every run; up to 144/day. §9: "accept for v1" | Cooldown plus per-prize daily cap. If you still accept flap, state the accepted ceiling as a number. |
| 9 | Slow drift, ~1 pt per run | Posts at cumulative 5 pt, because the baseline is last-*posted* not last-*observed* — correct, but the doc never says this is the intent | State it as an intended property and add a test for the accumulate-then-post case. |
| 10 | `DEPRIZE_ODDS_WIRE_CHANNEL_ID` unset | 200 `{ skipped: true }` (§8) | Keep, but count it in the response so a permanently unconfigured wire is visible rather than a green no-op. |
| 11 | Wrong channel id or missing bot permission (403 / 404) | `boolean` false, indistinguishable from a 429, retried every 10 min forever, silently | Non-retryable classification, one alert, stop retrying that prize. |
| 12 | `serverMarket` RPC fails for one prize in the loop | Unspecified; likely throws and abandons the remaining prizes | Per-prize try/catch: do not advance that prize, continue the others, report in `errors`. |
| 13 | Non-finite probability from a bad read | `shouldPostOddsWire` false (review patch — correct) | Also: do not advance the baseline, or a bad read poisons the comparison state. |
| 14 | Two runs overlap (dispatch during schedule) | Both read the same baseline, both post | `SET NX EX` lock per prize. |
| 15 | Malformed / hand-edited snapshot JSON | Unspecified; throws → red Action with no diagnosis | Treat as `previous = null`: no post, reset, report. Mirror `parseStoredCursor`. |
| 16 | Cron returns 200 with `errors` non-empty | `curl -fsS` passes → **Action green while the wire is broken** ([`deprize-reconcile.yml`](../../.github/workflows/deprize-reconcile.yml) line 20) | Non-2xx on hard failure, or a `jq` assertion on `errors == []` in the workflow. |

## 4. Recommended doc edits, in order

1. Rewrite §6.4 around a pure `nextOddsWireSnapshot({ previous, current, posted })` with the six
   transitions from M1, and add `{ p, outcomeCount, postedAt }` as the stored shape. Cite
   `nextReconcileCursor` as the precedent. (M1, M2, table rows 3–6, 9, 13)
2. Add `ODDS_WIRE_MIN_INTERVAL_MIN` and a per-prize daily cap; read the `postedAt` you already
   store. (M3, row 8)
3. Add resolved/superseded skipping to the cron loop. (M7 of the table — row 7)
4. Choose branch (a), the 2000 ms race, as the v1 ACK strategy; move deferred to a follow-up; add
   `DISCORD_APPLICATION_ID` to the interactions row of §6.5 if deferred survives. (M4)
